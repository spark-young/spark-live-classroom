# 章节树 / 分类树存储设计评估

> 对象:分类 `tc_category`(pid 邻接表)与章节 `tc_chapter`(nid/crid 双指针邻接表 + `tc_chapter_root_first` 根索引)
> 结论版本:2026-09 评估,基于仓库当前代码(`backend`、`front/live-room`、`sql/spark_live.sql`)

---

## 1. 结论摘要(先看这段)

- 章节的「nid/crid 双指针 + 根索引」是作者在 **MySQL 5.7 无递归 CTE + 同级必须保序 + 整课单查询还原** 三大约束下做出的自洽设计,替代掉了维护成本更高的旧「section 路径串 + sort 序号」方案,演进动机真实。
- 但放在本项目的真实规模(每课几十个节点、班级 1~20 人、单机演示)与真实操作集合(只支持尾部追加 / 首子插入 / 整棵删除,无任意位置插入与拖动排序)下,**该设计并非必要**:核心收益(行级 O(1) 前后继重链)没有被使用,却引入了失链风险、无父指针、无 `cid` 索引、子树/路径查询缺失等代价。
- 若要继续演进(任意插入、拖动排序、面包屑/节号、子树统计),建议重构为 **pid 邻接表(+兄弟 lexorank/order)**;允许升级 MySQL 8 则 `pid + WITH RECURSIVE` 最省。重构时务必保持 `tc_schedule.chid` 对章节行的行级引用语义。

---

## 2. 事实澄清:README 表述修正

仓库 README 中「分类用 pid 邻接表递归建树」的表述**只成立在表结构与设计文档层面,不在运行代码层面**:

- `CategoryServiceImpl.getCategoryList()` 仅查询全部 `status=1` 的分类,返回**扁平列表**,无任何递归/组树逻辑;
- `tc_category` 种子数据 9 个分类 `pid` 全部为 0(实际只用一层);
- `sql/无限分类数据库设计.md` 只有一句话方案:"后端根据 pid/id 构建树形实例对象,再根据 fastjson 转为树形 JSON",是意图而非实现。

**真正实现了「无限层级有序树」的是章节**,分类目前只是"支持多层级的扁平列表"。因此本文以章节为主评估,分类仅作对照。

## 3. 现状还原(基于代码)

### 3.1 表结构

```sql
tc_category(id, title, description, pid, status, ...)        -- pid=0 为根,经典邻接表
tc_chapter(id, cid, title, description, url,
           nid,  -- 同级下一个兄弟章节 id,0=无
           crid, -- 第一个子节点 id,0=无
           section, sort, status, ...)                        -- section/sort 为旧方案残留列
tc_chapter_root_first(cid, chid)                              -- 每门课的首根章节索引,PK=cid
```

无任何外键;`tc_chapter` 除主键 `id` 外**没有 `cid` 二级索引**。

### 3.2 读路径(整课单查询 + 内存 BFS)

`CourseServiceImpl.getCourseDetails()` / `getChapter()`:

1. 一条 SQL 取回整课全部章节(`ChapterMapper.getChapterByCourseId` 等,按 `cid` 过滤);
2. 从 `tc_chapter_root_first` 取首根 `chid`,构造虚拟根(id=-1,crid=首根);
3. `getChapterToList()/getChapterToTree()`:HashMap 建 id→节点索引,队列 BFS —— 取 `crid` 找孩子、沿 `nid` 遍历兄弟,还原**有序多叉树**后 fastjson 序列化输出。

### 3.3 写路径(仅"追加/首子/删除")

- `insertChapterRoot`:新行 `nid=0,crid=0`;若传入 `preChid` 则 `pre.nid = 新id`(追加到根链末尾);无 `chapter_root_first` 则登记新根。
- `insertChapterNode`:同上;`preChid != 0` → 作为前驱的**后继追加**;否则 `parChid != 0` → 作为父的**首子**(父 `crid = 新id`)。
- `deleteChapterNode`:接收**整棵子树 id 数组**,删除后仅按第一个 id 重链一次(`pre.nid` 或父 `crid` 或 `chapter_root_first` 指向其后继)。
- `updateChapterNode`:仅改标题/简介/url,不动结构。

前端(`courseListTeacher.vue`)的操作面与之严格匹配:加根章节=追加到根链末尾(`preChid = 最后一个根 id`)、节点下"添加"=追加为其最后一个孩子 / 首子、删除=收集子树后整删。**不存在任意位置插入与拖动排序**(`vuedraggable` 已装但全项目零引用)。

### 3.4 演进痕迹(为什么要重写)

代码与数据中保留了一套**已被废弃的旧方案**:

- `tc_chapter.section` 注释:"`[1,1,3]`表示第一章 1.3 节"(物化路径字符串);
- `sort` 列 + 旧查询 `order by sort`(序号排序);
- 被注释的旧 `getChapterToList()`(按 section 切分逐层下钻聚合),标注"暂废弃使用";
- 种子数据中 `section` 已全部为 `'1'`、`sort` 大量为 0 —— 证明旧字段停止维护,顺序与层级信息整体迁移到 `nid/crid` 指针。

即:作者先实现「物化路径 + 序号」,发现插入/删除要重排整批序号、路径串维护繁琐,后重写为「双指针 + 根索引」。

## 4. 设计动机:解决了什么问题

真实约束:

1. 章节是**有序树**:大纲式教材结构,同级先后有教学顺序,层级不限(设计意图);
2. **MySQL 5.7 无递归 CTE**,无法在 SQL 内 `WITH RECURSIVE` 求子树/路径;
3. 读模式是**整课一次渲染**(课程详情、章节管理均输出整棵有序树);
4. 写模式只有三类:加孩子 / 加根章节 / 删除(可带子树)。

方案回答:

| 要解决的问题 | 双指针方案的答案 |
|---|---|
| 同级保序,避免重排 | 顺序即 `nid` 链表结构;追加只需新行 + 改 1 行前驱/父指针,无整批重排 |
| 无限层级、插入后无整串维护 | 无深度列/路径串;深度只体现在指针链长度 |
| 无 CTE 下单查询还原整树 | 1 条 SQL 全量取回 + O(n) 内存 BFS |
| 指针树没有"入口" | `tc_chapter_root_first` 登记每课首根(相当于每课一份指针森林的根目录) |
| 替代旧方案的痛点 | 彻底绕开「section 路径重写 + sort 序号重排」 |

评价:**在其目标约束下自洽且写路径最省,替代旧方案是合理演进。**

## 5. 代价与风险

### 5.1 正确性:库级零保护,链靠应用自觉

- 无外键、无唯一约束,`nid/crid` 为普通 int,`0` 同时兼任"空指针"与字段默认值;
- 业务代码**无事务、无自愈**:任何一步写失败/并发交错即产生不可达孤儿,且只在下次读树时暴露;
- 插入语义只支持"追加":`preChid` 若已有后继(`nid≠0`)会被直接覆盖,**旧后继失链**;`preChid`/`parChid` 同时为 0 会插入不可达节点。前端调用路径恰好避开,但 API 层无防护;
- 删除整棵子树依赖调用方**一次传齐全部后代 id**,漏传即残留。

### 5.2 表达力短板

- SQL 无法回答"祖先链 / 子树大小 / 层级路径 / 节号",只能整课全量取回再内存走链;
- 节点**无父引用**,移动子树 / 拖动换父 / 面包屑都要新增逻辑(现有结构不支持,需通用重链);
- 排序、父关系、层级被编码进两个指针,心智负担高。

### 5.3 性能隐患

- `tc_chapter` 无 `cid` 二级索引,按课程读树 = 全表扫描(演示规模无感,量级上来即隐患)。

本质:把内存里的"孩子兄弟链表"直接持久化进关系库,结构优雅、工程易碎。

---

## 6. 是否有必要:分层面回答

- **就其自身目标(无 CTE、保序、整课单查询)**:**必要且自洽**,明显优于被替代的 `section+sort`。
- **就本项目真实规模与操作集合**:双指针的核心收益「行级 O(1) 前后继重链」**从未被使用**(无任意插入、无拖动排序),**不必要**,属于"更漂亮而非更稳妥"的选型。pid 邻接表 + 排序字段即可达到同等效果,且不变量直观、不会静默失链。
- 教学演示语境下可作为"树存储方案探讨"的素材,但**不建议作为长期维护的默认选型**。

## 7. 替代方案对比(针对本项目约束)

| 方案 | 组树 / 读 | 插入 / 删除 | 子树 / 路径 / 祖先 | 适配评价 |
|---|---|---|---|---|
| **pid 邻接表 + order/lexorank**(分类同族) | 1 SQL + 内存按 pid 聚合 + 排序 | 简单;中间插入用间隔编号(如 lexorank)可避免整批重排 | 递归求(5.7 需应用层递归/N 次查) | **首选替代**;直观成熟,保留行级可寻址 |
| **物化路径**(祖先 id 串 / 旧 section) | 前缀 `LIKE` 取子树 | 移动/中间插入需重写**整棵后代**路径 | 最快 | 作者弃用过的方案;适合只读菜单,不适合编辑型 |
| **闭包表**(ancestor/descendant/depth) | 任意子树/移动一条 SQL | 写放大、删改复杂 | 最强 | 大纲编辑场景过重 |
| **嵌套集 left/right** | 子树统计一行解决 | 插入/删除重算大段区间 | 强 | 层级与顺序稳定时可用;心智与维护成本高 |
| **MySQL 8 `WITH RECURSIVE` + pid** | SQL 直接递归 | 同邻接表 | SQL 级解决 | 允许升 8.0 时**双指针失去存在理由** |
| **整树存 JSON 文档** | 一次读 | 整树覆盖写 | 无 | ⚠️ **不可行**:`tc_schedule.chid` 按章节 id 关联排课,章节必须**行级可寻址** |

**关键约束**:`tc_schedule(chid)` 以章节行为引用对象做排课,替代方案必须保留"每行可独立被 id 引用",排除了整树单文档存储。

## 8. 建议

1. **维持现状运行**:没问题 —— 现有前后端只在指针方案受支持的路径(追加 / 首子 / 整棵删除)上工作;
2. **扩展功能前重构**:出现以下任一需求即触发重构 —— 任意位置插入、拖动排序、节号/面包屑、子树统计、并发编辑;
3. **重构方向**:MySQL 5.7 下选「pid + 兄弟 lexorank(或 order 列)」;可升 8.0 直接 `pid + WITH RECURSIVE`;闭包表仅当"任意子树查询/移动"成为高频需求;
4. **重构底线**:保留章节行级 id 引用(`tc_schedule.chid` 等),不破坏已有排课/订阅数据语义;补事务与一致性校验。
